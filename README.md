# SUPERKVN - (почти) неубиваемый kvn
[![GitHub Repo stars](https://img.shields.io/github/stars/soadmized/superkvn-pro?logo=github&style=flat-square)](https://github.com/soadmized/superkvn-pro)
---
**SUPERKVN** поднимает VLESS + XHTTP + TLS: nginx обслуживает сайт и передаёт транспорт во внутренний Xray. Устойчивость к блокировкам зависит от сети и не гарантируется.

## 🚩 Предусловия  🚩
Перед развертываением проекта у вас уже должны быть:
- Сервер (`vps`/`dedicated`) с Linux, Docker Engine 28+ / Compose v2, GNU Make, `envsubst` (пакет `gettext-base`), `openssl` и `cron` (для автопродления SSL), расположенный за пределами РФ
- Зарегистрированный домен, указывающий на сервер (`A-запись`/`A-record`)
- Порты `80` и `443` открыты

## Особенности
SUPERKVN автоматически поднимает сайт, nginx, 3x-ui, получает SSL-сертификаты от Let’s Encrypt и создает настроенный входящий узел (inbound) в 3x-ui.
Транспорт по умолчанию — XHTTP `stream-up` через HTTP/2. Внешний TLS завершает nginx, между nginx и Xray используется HTTP/2 без TLS внутри Docker-сети. Панель опубликована только на loopback VPS и доступна через SSH-туннель. Legacy WS оставлен для миграции и отката.

## Как использовать

### 1. Клонируем репозиторий
```bash
git clone https://github.com/soadmized/superkvn.git
cd superkvn
```

### 2. Настройка переменных окружения
Скопируйте `.env.dist` в `.env` и заполните значения:
```bash
cp .env.dist .env
nano .env
```
**Важные параметры:**
- `DOMAIN`: Ваш домен (должен быть заранее направлен на IP сервера).
- `EMAIL`: Для уведомлений от Let's Encrypt.
- `UI_PORT`, `UI_DUMMY_PATH`, `UI_PATH`: Локальный порт и путь панели (путь не является защитой).
- `NETWORK_TRANSPORT`: `xhttp` (по умолчанию) или `ws` для временной совместимости.
- `NETWORK_PATH`: Путь без начального/конечного слеша; для XHTTP генератор добавляет оба слеша.
- `TLS_FINGERPRINT`: `chrome` по умолчанию; также допускаются `firefox` и `safari`.
- `NETWORK_PORT`: Внутренний порт Xray, отличный от порта панели.

На клиентах требуется поддержка XHTTP `stream-up` и параметров VLESS-ссылки `mode`, `fp`, `alpn`.
Проверьте фактическую конфигурацию после импорта в Happ / Default VPN: `type=xhttp`,
`mode=stream-up`, `security=tls`, `alpn=h2`, `fp=chrome` (либо выбранное значение),
правильные Host/SNI и путь. Проверка сертификата должна быть включена.
Обычный TCP Mux (`mux.cool`) отключите; XHTTP использует встроенный XMUX с настройками ядра по умолчанию.
Единый профиль не гарантирует одинаковую поддержку в разных версиях приложений.

### 3. Быстрый запуск (рекомендуется)
Все шаги (подъем HTTP, выпуск SSL, настройка 3x-ui и перезапуск на HTTPS) выполняются одной командой:
```bash
make deploy
```

### 4. Где взять данные для подключения?
После выполнения `make deploy` все необходимые данные будут сохранены в файл `~/creds.txt` (в домашней директории пользователя):
- Логин и пароль от панели 3x-ui.
- Ссылки `vless://` включённых клиентов для импорта в приложение с поддержкой XHTTP.

Секретные ссылки и пароль не публикуйте. Файл создаётся с правами `600`.

## Ручное управление (если не использовать deploy)

### Шаг 1: Поднимаем Nginx (только HTTP)
```bash
make nginx-http
```

### Шаг 2: Получение SSL-сертификата
```bash
make ssl-init
```

### Шаг 3: Настройка 3x-ui
Сначала запускаем контейнер Xray (порт панели уже закрыт от внешней сети), затем настраиваем:
```bash
make xray-up
make 3xui-init
```

### Шаг 4: Перезапуск с HTTPS
```bash
make restart
```

## Добавление нового клиента

На сервере с уже настроенным inbound выполните из каталога проекта:

```bash
make 3xui-add-client CLIENT_NAME=phone
```

Команда создаёт включённого клиента с отдельным UUID без лимита трафика и срока действия
и выводит его ссылку `vless://...` в терминал. Скопируйте её для импорта в приложение.
Ссылка не записывается в `~/creds.txt`. Без `CLIENT_NAME` имя генерируется автоматически.
Для имени подходят латинские буквы, цифры, `_`, `@`, `.` и `-` (кроме `.` и `..`);
повторное использование существующего имени завершится ошибкой.

Inbound выбирается по `INBOUND_REMARK` (по умолчанию `DOMAIN-NETWORK_PORT`) или `NETWORK_PORT`.
Команда требует единственного совпадения и проверяет порт, VLESS, выбранный транспорт, путь,
режим и отсутствие внутреннего TLS. При несовпадении настроек клиент не создаётся.
Начальные ссылки и ссылки новых клиентов формируются одним генератором; TLS завершается
на nginx, внешний порт — 443.
Используется пароль панели из первой строки `~/creds.txt`; при другом расположении
укажите `CREDS_FILE=/путь/к/creds.txt`.

## Доступ к панели

На ноутбуке откройте SSH-туннель (замените `4242` на ваш `UI_PORT`):

```bash
ssh -N -L 127.0.0.1:18080:127.0.0.1:4242 root@SERVER_IP
```

Затем откройте `http://127.0.0.1:18080/dummy/path/`, подставив ваши
`UI_DUMMY_PATH` и `UI_PATH`. HTTP здесь проходит внутри SSH-туннеля.
Публичных маршрутов панели в nginx нет, включая старый редирект и «пустышку».
Порт Xray не публикуется на хосте. Секретные пути не заменяют ограничение доступа.
Docker Engine 28+ указан из-за исправления доступности localhost-публикаций из соседней L2-сети.
С внешнего устройства проверьте недоступность порта панели по IPv4/IPv6 и старого URL.

## Переход существующего WS-сервера на XHTTP

Переход меняет транспорт на том же inbound: UUID, список клиентов и лимиты сохраняются,
но **старые WS-ссылки перестают работать до отката**. Это короткое окно обслуживания;
заранее проверьте поддержку XHTTP во всех приложениях и сохраните старые профили.
Сделайте согласованную резервную копию БД панели перед обновлением её образа.
Команда миграции также сохраняет JSON исходного inbound с правами `600`
в `db/transport-backups/` (содержит секреты).

1. Если нужно сначала закрыть панель и сохранить WS, укажите в `.env` `NETWORK_TRANSPORT=ws`,
   затем выполните `make up`. Этот шаг также подключит новые скрипты к контейнеру.
2. Поменяйте в `.env` `NETWORK_TRANSPORT=xhttp`, добавьте `TLS_FINGERPRINT=chrome`.
   Оставьте прежние `NETWORK_PORT`, `NETWORK_PATH`, домен и реквизиты панели.
3. Выполните:

```bash
make 3xui-migrate-transport
```

Команда пересоздаёт контейнер при изменении Compose, применяет настройки панели,
проверяет единственность и тип inbound, сохраняет его копию, меняет транспорт,
проверяет nginx и запускает HTTPS. Новые ссылки всех включённых клиентов дописываются
в `~/creds.txt`; их также можно вывести командой `make 3xui-export-links`.
Повторный `make deploy` или `make up` не заменяет миграцию: несовместимый существующий
inbound вызывает ошибку, а не молча принимается за настроенный XHTTP.

Импортируйте новые ссылки на всех устройствах и проверьте загрузку, выгрузку,
простой и переподключение. После изменения шаблонов требуется пересоздание nginx:
один `docker compose restart` не пересобирает конфигурацию.

Для отката верните в `.env` `NETWORK_TRANSPORT=ws` и снова выполните
`make 3xui-migrate-transport`. UUID сохранятся, старые WS-профили заработают;
панель останется закрытой. Если ошибка возникла после изменения inbound, прежде
чем менять настройки повторно, проверьте `make 3xui-inbound-exists` и логи контейнеров:
автоматического повторения изменяющих API-запросов нет.

## Проверка изменений

```bash
python3 -m unittest discover -s tests -v
```

Требуются Python 3, `jq`, `envsubst`, Make. Тесты используют поддельный API и не обращаются к VPS.
Дополнительные проверки в одноразовых Docker-контейнерах:

```bash
python3 tests/integration_xhttp.py
python3 tests/integration_panel.py
```

Они проверяют настоящий туннель (TLS, загрузка/выгрузка 2 МБ, переподключение),
ответы 404 на старых путях панели, создание/миграцию/откат через API и localhost-публикацию
порта в Compose. Используют тестовые сертификаты и пустую БД, не читают рабочую `.env`,
не публикуют порты; могут скачивать образы и пакеты. Проверено с Xray 26.7.11 и nginx 1.31.8.
Работа конкретных версий Happ / Default VPN и доступность из сетей пользователей
проверяются отдельно после импорта профиля; эти тесты не измеряют устойчивость к ТСПУ.

Документация транспорта: [XHTTP](https://github.com/XTLS/Xray-core/discussions/4113),
[параметры TLS](https://xtls.github.io/en/config/transports/tls.html).

## Полезные команды
- `make 3xui-add-client CLIENT_NAME=phone`: Создать клиента и вывести ссылку подключения.
- `make logs`: Просмотр логов Nginx.
- `make ssl-renew`: Ручное обновление сертификатов.
- `make cron-install`: Установка автопродления сертификатов в crontab.
- `make down`: Остановка всех контейнеров.
- `make gen-pass`: Создать пароль, если файла ещё нет; существующий пароль сохраняется.
- `make 3xui-export-links`: Вывести актуальные ссылки всех включённых клиентов.
- `make 3xui-migrate-transport`: Явно сменить WS/XHTTP с сохранением UUID.
